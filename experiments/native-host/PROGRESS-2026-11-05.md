Work is paused at the user's request after the latest device tests. The new

## Product hypothesis

The new native host is a viable prototype direction: React/JSX and selected React
Native primitives drive real platform views through a small renderer, Hermes,
Yoga, native bindings and a Rust service core. The development pipeline now uses
Rolldown, a permanent React Refresh bootstrap and ordered Rust delivery. These
results support the architecture's feasibility. They do not yet establish its
overall performance advantage, production readiness or broad RN compatibility.

Seven primitives are implemented: View, Text, Image, Pressable, TextInput,
ScrollView and WebView. Native commands and the real AppState service have device
evidence. WebViews are native primitives, with their own document and lifecycle
boundaries. Development ingress is separately gated from test evaluation and
excluded from Release artifacts. No Tauri runtime dependency was added.

The full RNTester app is the reference baseline, retaining its larger module and
native graph. Both products run the byte-identical shared 100-row screen through
their respective renderer adapters. The candidate does not yet run all RNTester
examples; different graph sizes and capabilities limit performance attribution.

## Performance evidence and limits

The earlier physical Pixel packet used 30 measured pairs plus three warmups:

| Earlier workflow | Full RNTester median | Candidate median |
| --- | ---: | ---: |
| Default development: RN Fast Refresh vs candidate full reload | 824 ms | 2,152 ms |
| Full process reload on both | 3,890 ms | 2,237 ms |

Those results motivated native Refresh. They do **not** measure the new update
path. The default-workflow run also retains its initial idle-iOS-process
concurrency caveat. The endpoint is an external OS accessibility observation,
including polling/IPC, not a compositor-present timestamp. See
`performance/RESULTS.md` for raw reports and version differences.

The new one-pair exercise and 30-pair comparison have not run. Controlled native
build, release startup, steady workload memory and frame-time comparisons remain
open. The working 20% improvement / 10% regression thresholds remain experiment
criteria, not approved product service-level objectives.

## Recommendation before resuming

Continue the native-host hypothesis through a bounded validation phase. Keep the
React semantic boundary and permanent runtime; use measurements to select further
Rust/tooling work. Defer expansion of the primitive/module surface until the
current behavior and benefit gates support it.

1. Review the latest iOS staging and native artifact-receipt changes.
2. Isolate the iOS inline-history failure against plain WKWebView and an explicit
   URL origin; determine whether it is host behavior, platform behavior or an
   unsupported source contract. Preserve the failing acceptance test meanwhile.
3. Run the one-pair functional exercise, then the reviewed 30-pair comparison
   against full RNTester during a quiet interval. Preserve every failure.
4. Measure controlled native builds, Release startup, memory and frame behavior,
   and extend browser lifecycle/storage/process-recovery checks.
5. Re-evaluate proceed/revise/reject using the complete behavior and performance
   evidence. A faster development edit alone is insufficient for final acceptance.

Implementation detail and the full evidence ledger remain in `VERIFICATION.md`.
